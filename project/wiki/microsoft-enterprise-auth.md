# Microsoft Enterprise Calendar Auth — Azure AD App Registration

## Context

Raised during client demo on 2026-04-27. First production test will be with client **Cos** (Microsoft tenant).

When a rep tries to connect a **Microsoft enterprise account** (Azure AD / Entra ID — i.e. a corporate `@company.com` account), the Nylas OAuth redirect fails or prompts for admin consent that never arrives. Personal Microsoft accounts (`@outlook.com`, `@hotmail.com`) work fine.

This is a **hard blocker** for any client whose reps use corporate Microsoft calendars.

## Root Cause

Microsoft's identity platform (Azure AD / Entra ID) requires that any OAuth app connecting to a corporate tenant be:

1. Registered as an **Azure AD multi-tenant application**, AND
2. Either granted **admin consent** by each tenant's IT admin, OR configured with user-consent policies that the tenant allows.

Currently, Nylas is used without a custom Azure AD app. Nylas's default Microsoft connector is not pre-approved by enterprise tenants, so corporate accounts hit the "admin consent required" wall.

## Redirect URI Architecture

The OAuth flow has **two distinct callback URLs** — don't confuse them:

```
Rep browser → Nylas auth URL → Microsoft login → Nylas's own callback → Your server callback
                                                  (api.us.nylas.com)    (MVP_NYLAS_CALLBACK_URL)
```

| Callback | URL | Where to register |
|---|---|---|
| **Nylas callback** | `https://api.us.nylas.com/v3/connect/callback` | Azure AD app → Redirect URIs |
| **Your server callback** | `MVP_NYLAS_CALLBACK_URL` (env var) | Nylas Dashboard → app settings |

- Azure AD never calls your server directly. It calls Nylas. Nylas exchanges the code for tokens, then redirects the browser to your server.
- The Nylas callback URL (`api.us.nylas.com`) is fixed — it never changes between dev and prod.
- Your server callback changes per environment — set `MVP_NYLAS_CALLBACK_URL` accordingly.

**Dev**: `MVP_NYLAS_CALLBACK_URL=http://localhost:8787/api/admin/integrations/nylas/callback`  
**Production**: `MVP_NYLAS_CALLBACK_URL=https://<PROD_DOMAIN>/api/admin/integrations/nylas/callback`

> Production URL unknown at dev time — DevOps must fill in `<PROD_DOMAIN>` and update the Nylas dashboard before first deployment. The Azure AD app registration does **not** need to change.

## What Needs to Be Done

### Step 1 — Create Azure AD App Registration

In [portal.azure.com](https://portal.azure.com):

1. **App registrations → New registration**
   - Name: `BeeNice Calendar`
   - Supported account types: **Accounts in any organizational directory (Any Microsoft Entra ID tenant - Multitenant) and personal Microsoft accounts**
     *(Not the "multitenant only" option — that would block reps using personal @outlook.com / @hotmail.com accounts)*
   - Redirect URI: Web → `https://api.us.nylas.com/v3/connect/callback`
     *(This is Nylas's fixed callback — not your server. Verify exact URL in Nylas Dashboard → Microsoft connector settings.)*
2. **API permissions → Add a permission → Microsoft Graph → Delegated permissions**:
   - `User.Read` *(usually pre-added by default — verify it's there)*
   - `Calendars.ReadWrite`
   - Do **not** add `offline_access` — it is an OAuth scope requested at runtime, not a portal permission
   - Do **not** add anything else (`Mail.*`, `Contacts.*` etc.) — unnecessary permissions trigger enterprise IT suspicion on the consent screen
3. **Certificates & secrets** → create a Client Secret, copy value immediately (shown only once)
4. Note the **Application (client) ID** and **Directory (tenant) ID**

### Step 2 — Configure Nylas Custom Microsoft Connector

In the Nylas Dashboard:

1. **Integrations → Microsoft** → "Use custom OAuth credentials"
2. Enter Azure App **Client ID** and **Client Secret** from Step 1
3. Under callback/redirect settings, confirm your **server callback URL** matches `MVP_NYLAS_CALLBACK_URL`
4. Save. Nylas will now route Microsoft OAuth through your registered Azure app.

> No code changes required in `mvp/server/lib/provider.mjs` — Nylas handles Azure credentials transparently.

### Step 2b — Production Deployment Checklist (for DevOps)

> Adam delivers the code. DevOps sets the production URL and completes these steps.

- [ ] Determine the production server domain (e.g. `app.benice.io`)
- [ ] Set env var: `MVP_NYLAS_CALLBACK_URL=https://<PROD_DOMAIN>/api/admin/integrations/nylas/callback`
- [ ] In **Nylas Dashboard** → app settings → update the callback URL to the production value
- [ ] Azure AD app registration requires **no changes** (Nylas's callback URL is always `api.us.nylas.com`)

### Step 3 — Admin Consent Per Client Tenant

Each corporate client (e.g. Cos) needs to grant consent **once**:

**Option A — Admin consent URL** (preferred):
Send the client's IT admin this URL (fill in your Azure `CLIENT_ID`):
```
https://login.microsoftonline.com/common/adminconsent?client_id=<YOUR_CLIENT_ID>&redirect_uri=<YOUR_REDIRECT_URI>
```
The admin clicks "Accept" → all users in that tenant can then authenticate without friction.

**Option B — User consent at first login**:
If the tenant allows user consent, the rep gets a "grant permissions" prompt on first OAuth. This works without IT admin involvement but is tenant-policy-dependent — less reliable.

### Step 4 — Test with Cos

After Steps 1–3:
- Have a Cos rep go through the calendar connection flow (`/api/admin/integrations/nylas/start`)
- Verify the callback succeeds and `connection.status` becomes `"connected"` in the DB
